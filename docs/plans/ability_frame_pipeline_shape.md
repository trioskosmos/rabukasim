# Ability Frame Pipeline Shape

This note describes the current ability pipeline after the cleanup that removed the source-file rewrite loop.

## End-to-end flow

The live path is:

1. `data/ability_frame_source.json` is the authored semantic ability source.
2. `tools/build_cards.py` compiles `data/cards.json` into `data/cards_compiled.json`.
3. Optional mirror sync copies the compiled runtime data into the launcher and engine mirrors.
4. Rust loads `data/cards_compiled.json` as the primary runtime card payload in `engine_rust_src/src/core/logic/card_db.rs`.

The important change is that the authored source is no longer regenerated by the build. It is edited directly, and compiled runtime data is derived from the raw card database instead.

## Source shape

`data/ability_frame_source.json` is intentionally text-first and compact.

Each ability entry keeps:

- `primary_text_jp`
- `primary_text_en`
- `source_ability_texts`
- `trigger_id`
- `trigger`
- `frames`
- `card_refs`

Optional authored metadata is preserved when present:

- `choice_flags`
- `choice_count`
- `is_once_per_turn`
- `requires_selection`

Generated report fields are not part of the authored contract anymore.

## Runtime shape

The runtime shape lives in `data/cards_compiled.json`.

That file contains executable card data, including the fully materialized `abilities[].frame_program.frames[]` that the Rust runtime executes.

The runtime does not reopen the authored source file at load time.

## Diagnostics

Diagnostics and issue sweeps should derive opcode lists from `frames` directly when they need them.

They should not depend on a generated `opcode_sequence` field in the authored source.
