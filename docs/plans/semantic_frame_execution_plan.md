# Semantic Frame Execution Plan

## Goal

Remove the interpreter's dependency on raw bytecode when a semantic frame program is already available.

Today, `Ability.frame_program` and `Ability.effects` already carry enough structure to execute many abilities without first flattening them into `Vec<i32>` and then decoding those words back into `BytecodeInstruction`.

The target is:

- execute `AbilityFrame` values directly when available
- keep bytecode execution as a compatibility fallback
- eliminate byte-shifting from the hot execution path for semantic abilities
- preserve existing behavior, logs, and test coverage

## Current State

Relevant code paths in `engine_rust_src`:

- `core/logic/interpreter/mod.rs`
  - `resolve_ability` currently prefers `frame_program`, but immediately converts it with `to_bytecode()`
  - `resolve_frames` also converts frames into bytecode before execution
  - the direct ability path already iterates over `ability.effects`, but still constructs `BytecodeInstruction` manually for dispatch
- `core/logic/models.rs`
  - `AbilityFrame::to_instruction()` converts semantic frames into `BytecodeInstruction`
  - `FrameProgram::to_bytecode()` flattens the semantic program for the interpreter
  - `Ability::bytecode_program()` still prefers raw bytecode and only falls back to a frame program
- `core/logic/interpreter/handlers/mod.rs`
  - `HandlerRegistry::dispatch` already accepts `&BytecodeInstruction`, but the dispatch path still treats the instruction like a packed bytecode record

## Design Principles

1. Keep execution on semantic objects whenever possible.
2. Preserve bytecode as an interoperability and serialization format, not the primary runtime path.
3. Centralize conversions at the edge, not in the interpreter loop.
4. Make handler APIs read like operand consumers, not bit-decoder consumers.
5. Avoid changing behavior unless a test proves the new path is equivalent.

## Proposed Execution Model

### Preferred path

When an ability has `frame_program`, execute it through a new semantic resolver:

- iterate `AbilityFrame` values directly
- map each frame to a semantic instruction view only when a handler needs one
- preserve `program_counter`, choice injection, branching, suspension, and return handling

### Fallback path

If a semantic frame program is missing, continue using existing bytecode execution.

That keeps compatibility with:

- older content
- sparse / generated bytecode sources
- any code paths that still rely on serialized instruction words

## Implementation Phases

### Phase 1: Add a semantic resolver

Introduce `resolve_semantic_frames` in `core/logic/interpreter/mod.rs`.

Responsibilities:

- accept `&[AbilityFrame]`
- execute frames without calling `to_bytecode()`
- preserve the same execution lifecycle as `resolve_bytecode`
- support suspension, branching, and `Return` semantics
- update `ctx.program_counter` from semantic frame index mapping

Recommended shape:

- `resolve_ability`:
  - if `frame_program` exists, call `resolve_semantic_frames`
  - otherwise, keep the bytecode fallback
- `resolve_frames`:
  - call `resolve_semantic_frames` directly

### Phase 2: Introduce a semantic instruction adapter

Keep `BytecodeInstruction` as the handler-facing structure for now, but create it from semantic frames without detouring through packed words.

This adapter should:

- build `BytecodeInstruction` from `AbilityFrame`
- avoid reconstructing from `Vec<i32>`
- remain the only place where frame-to-instruction conversion happens

If handler code still needs raw fields like `raw_s`, keep them available temporarily, but do not let the interpreter depend on raw encoding logic.

### Phase 3: Make dispatch semantic-first

Update `HandlerRegistry::dispatch` so it consumes a semantic instruction object rather than a raw bytecode slice.

This should remove the remaining coupling between dispatch and bytecode layout.

Recommended adjustments:

- dispatch should not require `bytecode: &[i32]` in the semantic path
- handlers should receive the semantic instruction and any explicit context they need
- if a handler truly needs the underlying word stream, isolate that as a legacy-only bytecode path

### Phase 4: Narrow `models.rs` responsibilities

Decide whether `AbilityFrame::to_instruction()` and `FrameProgram::to_bytecode()` are still needed for runtime execution.

Likely outcome:

- keep them only for serialization, debugging, and compatibility tests
- stop calling them from interpreter entry points
- consider renaming or relocating them if they become codec helpers rather than runtime helpers

If these helpers are still useful elsewhere, do not delete them prematurely. The main requirement is that they no longer sit on the execution path.

### Phase 5: Reduce operand decoding inside handlers

Inspect handlers for places where they decode raw packed fields repeatedly.

Examples of likely cleanup:

- prefer typed accessors such as `slot()` and `filter_attr()`
- avoid manual bit extraction in handler bodies
- move opcode-specific operand interpretation into small helpers where it is shared

This is the step that turns the interpreter from "bytecode aware" into "semantic operand aware".

## File-Level Change Plan

### `engine_rust_src/src/core/logic/interpreter/mod.rs`

- add `resolve_semantic_frames`
- route `resolve_frames` through the semantic resolver
- change `resolve_ability` to prefer direct frame execution when `frame_program` exists
- keep `resolve_bytecode` untouched except where shared lifecycle helpers can be reused

### `engine_rust_src/src/core/logic/interpreter/handlers/mod.rs`

- update `HandlerRegistry::dispatch` to accept the semantic instruction type used by the new resolver
- remove dependency on `bytecode: &[i32]` from the semantic path
- keep a bytecode-specific compatibility path only if an opcode truly needs it

### `engine_rust_src/src/core/logic/interpreter/instruction.rs`

- ensure `BytecodeInstruction::new` remains the canonical constructor for semantic instructions
- add any missing helpers needed by handlers so they do not inspect raw packed words directly
- avoid adding new bit-shift decoding into the interpreter hot path

### `engine_rust_src/src/core/logic/models.rs`

- keep `AbilityFrame` as the semantic source of truth
- stop using `FrameProgram::to_bytecode()` from interpreter entry points
- retain conversion helpers only if they are still needed for codecs, tests, or export paths

## Verification Plan

### Automated tests

Run the interpreter-focused tests first:

```bash
cargo test --package loveca-copy --lib -- core::logic::interpreter
```

Then run the higher-coverage QA batch:

```bash
cargo test --package loveca-copy --lib -- qa::batch_1
```

Additional recommended checks:

- any tests that exercise `resolve_ability` through `Ability.frame_program`
- any tests that verify suspension and resumption from `choice_index`
- any opcode-specific tests that inspect handler dispatch paths

### Manual verification

Confirm debug traces still show the same effect order and branching decisions, but without the frame-to-bytecode round-trip.

Look for:

- identical ability outcomes
- identical resume points
- identical branch behavior
- no unexpected changes in log formatting

## Risks

1. `program_counter` mapping can drift if semantic frame indices are not translated consistently to bytecode-style IP values.
2. Suspension and resumption may break if choice injection still assumes bytecode word positions.
3. Some handlers may still rely on bytecode-specific assumptions hidden in helper functions.
4. Removing conversion helpers too early could break tests or serialization tooling that still needs them.

## Acceptance Criteria

The work is done when:

- abilities with `frame_program` execute without calling `to_bytecode()`
- `resolve_frames` no longer routes through bytecode conversion
- handler dispatch works with semantic instruction input
- existing interpreter and QA tests continue to pass
- debug traces remain behaviorally equivalent

## Suggested Rollout Order

1. Add `resolve_semantic_frames` and wire `resolve_ability` / `resolve_frames` to it.
2. Move frame-to-instruction conversion into a single semantic adapter.
3. Update `HandlerRegistry::dispatch` to consume the semantic instruction type.
4. Trim or relocate conversion helpers in `models.rs`.
5. Run interpreter and QA tests, then fix any handler assumptions that surface.

## Notes

- Do not delete bytecode support yet.
- Do not widen the refactor to unrelated interpreter cleanup unless it blocks the semantic path.
- Prefer small, testable moves over a full rewrite of the interpreter loop.
